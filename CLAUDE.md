# CLAUDE.md — Instructions for AI developers

0. **Measure before implementing, and say so when an instruction is wrong.** Every expensive bug in this repo so far came from trusting a description instead of the wire: the spec (D26), the PDF (D14/D15), upstream's own error text (D38/D39/D40), a 200 response (D42/D43), and twice an instruction in this file that a probe then disproved. When a task says to do X and measurement shows X is not how upstream behaves, **implement what is true, and explain why the instruction changed** — do not implement the instruction and let the discrepancy surface later. Recording a problem is worth more than silently working around it. This rule outranks the rest.
1. **Read `OpenDrive-Bridge-Whitepaper.md` in full before writing any code.** It is the single source of truth for scope, architecture, phases (P0–P6), and quality gates. Appendix D lists non-negotiable rules.
2. Follow the phase order in whitepaper §5. Do not skip exit criteria. Current release line: **1.0.0 — the first release, not yet final: the S3 gateway and mount (whitepaper §3.6, phases S0–S3) are part of it.** v1.0.0-rc.1 (no S3) is an internal test build. The S3 gateway is the project's main purpose — backup software speaking S3 to the bridge, other software through a mounted folder — and §3.6.4's two constraints (unsent objects visible in listings; writes accepted while OpenDrive is unreachable) are preconditions, not polish. Derek reset the version numbering on 2026-09-27: the design that had been planned as 1.3 (sign in instead of preparing a file, `docker compose up -d`) is 1.0.0, and everything earlier is ignored. The v1.0–v1.2.1 tags and releases were deleted. **Version numbers elsewhere in this file, in code comments, in the whitepaper's changelog and in docs/discrepancies.md ("since v1.1", "until 1.3") are development milestones from before the reset, kept as history — never write one into anything a user reads.** Whitepaper document versions are a separate series and were not reset. P0–P6 are complete.
   - P3 delivered the upload pipeline (`upload.go`), the error classification layer (`classify.go` + `docs/error-taxonomy.md`), the download pipeline (`download.go`) and the job engine (`internal/jobs`).
   - P4 delivered the Bridge REST API (`internal/server`, 25 operations), `odctl` (`internal/cli`), `docs/bridge-openapi.yaml` with a CI drift check that walks the router in both directions, and `docs/bridge-boundary-audit.md`. **The Bridge boundary is where upstream's lies stop, and that property is now load-bearing rather than aspirational**: a resource-pressure refusal never surfaces as "permission denied", an empty archive is never reported as a successful download, a 200 is never taken as proof that anything happened, and a file that was just uploaded but is not yet visible never reads as "no such file". Each has a test at the Bridge layer, and the audit checks all 53 discrepancies one at a time — every one is either stopped there or written down in the OpenAPI spec so a caller can plan for it. Anything added to the API from here owes the same treatment.
   - **Every gate runs on every change.** The release workflow adds the publish step and nothing else. This rule was earned four times in one evening: `gosec` failed the first release dry run on three findings that had been reviewed months earlier but only written down in a document; `gitleaks` found a real access token committed weeks before by a test written to prove tokens do not leak; `trivy` found twelve HIGH findings in the Go standard library compiled into the image, because the Dockerfile's builder had been left on an old Go while everything else moved on; and the `macos-13` smoke job had been silently queueing for a runner GitHub retired in December 2025. Each was invisible until someone tried to ship. A gate that only runs at release time is not a gate, it is an ambush — and the same argument applies to any version pinned by hand next to something that floats.
   - P5 delivered goreleaser, the dual-architecture container and a release flow that has now published a real tag: six archives with checksums, an image tagged with its version and nothing else, and the published darwin/arm64 archive downloaded, checksum-verified and driven through the whole smoke suite as a user would receive it. Two bugs were only visible on the publish path, which no dry run reaches — `latest` was being pointed at a release candidate, and every line of the release notes began with a 40-character hash. A third came with v1.2.0: tagging the final release on the commit its last candidate was verified on — which is what a candidate is for — put two tags on one commit, goreleaser guessed the wrong one, and the release was left with an image and no binaries. The workflow now tells goreleaser the tag, and which tag the changelog starts from.
   - P6 delivered fuzzing and the transfer benchmarks (rule 5), `docs/first-run.md`, `docs/maintenance.md`, and the copyright decision: OpenDrive's guide is out of the repository and out of its history (rule 7). `docs/maintenance.md` is now the standing plan — weekly drift check, monthly dependency PR, and a support window of the newest minor plus security fixes for the one before it.
   - **Walking the documentation is a release gate, not a courtesy.** Following `docs/first-run.md` as written, on an account whose root is read-only, found two things no test had: every failed transfer exited 4 ("trying later is reasonable") even when the Bridge had already decided it was permanent, and every failed job reported the classifier's diagnosis rather than the wording written for a person — because that translation only ran for synchronous failures, and every upload is a job. Do this again before each release.
   - The original P5 description, kept because the reasoning still applies: P5 was goreleaser, the container and the release flow. The emphasis moves from "the code is correct" to "it installs, it runs, and when it breaks the person reading the message can tell why" — the readability standard the error wording already meets, applied to deployment. Two rules earned here: cross-compiling is not evidence, so every platform that has a runner boots the real daemon against the mock upstream and drives it with the real CLI; and a container has no keyring, so the "no persistence = configuration error" gate is the first thing a container user meets and must answer in a sentence, not a stack trace.
   - New bindings follow the folder module's pattern: a service struct, one method per endpoint with the verb and session placement in its doc comment, a row in the module contract test (`folder_contract_test.go` shows the shape), and a recorded fixture in `testdata/fixtures/` for anything whose response shape came off the wire.
   - **Probe the live API before writing a binding.** Six of the discrepancies so far (D26, D28, D30, D31 among them) were spec-versus-reality gaps that mock tests happily passed. Every boolean parameter in particular must be settled on the wire: `file/move_copy` takes only the strings `"true"`/`"false"`, `file_edit_online` only an integer, and `folder/move_copy`'s documented boolean `false` is refused outright.
   - **A probe that counts acceptances measures luck.** The §10.2(b) probe's first live run saw four concurrent out-of-order chunks all accepted and a matching close hash, and its conclusion branch said to implement `parallel_chunks`. They had merely arrived in offset order; the next runs refused them (D49). Ask the question in a form timing cannot answer for you — make the out-of-order requests *finish* before the in-order one is sent — and judge by the stored bytes read back, never by what close says.
   - **Nothing the engine is about to delete for good may rest on the engine's own belief.** Reclaiming an "interrupted" upload used the no-trash delete, and the engine believed an upload was interrupted whenever its record said running — which was also the state of a finished upload during the D44 wait, and for a moment after `finish()` had told the user it succeeded. A flaky test (`TestProgressIsPersistedAsItHappens`) was the only symptom. `reclaim` now asks upstream first (D52), and `finish()` saves before it publishes. A flaky test in `internal/jobs` or `internal/datacache` is a durability bug until shown otherwise; do not re-run it green.
   - Existence checks use the parent listing or `idbypath`, never `folder/info.json` (D27). Files differ: `file/info.json` does report a removed file as gone.
   - **Never leave an upstream artefact behind.** A record `create_file` made and did not fill is invisible to the user, and enough of them in one folder make upstream refuse further writes there (D39). `Upload` reclaims its own record unless told to keep it; integration tests must clean up every artefact, intermediate ones included.
   - Credentials go through `opendrive.CredentialStore` only; `internal/keystore.Open` chooses the backend. An absent credential file is the normal first state, not a configuration error: the daemon starts and asks to be signed in. What is not allowed is a sign-in that could not be saved reading as one that was — `POST /v1/auth/login` answers 503 `keystore_unavailable` then. `MemoryTokenStore` is test-only and reports itself ephemeral. Never introduce another path that stores a password.
   - **There is one credential backend: `credentials.key` beside the binaries (`/data` in the container), written by the daemon when someone signs in (§9.2.2, v1.3).** Nobody prepares it: signing in on the web page or with `odctl login` is the only step, and a password OpenDrive stops accepting puts the bridge back into "sign in again" without a restart. That replaced v1.1–v1.2's `.env` + `.env.key`, which the user had to copy from `.env.example`, fill in by hand and let the first start encrypt — Derek's call after trying it, because every preparation step was one more thing to know before anything worked. The file is one key line plus AES-256-CBC in OpenSSL's own container under a comment carrying the recovery command, and that command is run *as written* against the real `openssl` in the tests. There is no Windows branch of any of this: v1.2 removed Windows (§8.1), and the old rule "on Windows tighten the ACL with icacls" is void.
   - **v1.2's caching gateway (`internal/datacache`) is the first thing here that holds the user's data, and that changes what a bug costs.** Everything before it could fail by refusing to do something; this can fail by losing a file somebody was told was stored. §3.5.2's four rules are the acceptance criteria and each has a test that tries to break it (`TestRule1`…`TestRule5`): a dirty entry is never evicted, `max_dirty_bytes` refuses the write rather than discarding anything, nothing is acknowledged before the journal is fsynced, a SIGKILLed process loses nothing it acknowledged, and shutdown drains and names what it could not finish. Rule 4's test really does fork a child and send it SIGKILL, because the property is "what survives when nothing gets to run" and an in-process approximation cannot show that. Do not weaken any of the five to make a change pass.
   - **Naming, and it is not pedantry: `internal/cache` is the metadata cache, `internal/datacache` is the data cache.** Config keys, log fields (`datacache_*`) and metric names may not be shared (§3.5.4). Losing all of the first costs one round trip per lookup; losing the second can cost somebody's file, and a reader who thinks "the cache" is one thing will reason about the wrong risks.
   - **A flush failure goes through the classification layer like everything else** (rule 3). The flusher reads `IsTemporary`/`Diagnosis` and never looks at a status code. A permanent refusal leaves the object dirty and records the reason — dropping it would destroy the only copy on the strength of one answer, and D39/D40 are two recorded cases of that answer being wrong about itself.
   - **`-race` passing on one platform does not mean race-free.** A data race in `internal/datacache` passed `go test -race -count=5` on macOS and failed on the first Linux run, because the goroutine scheduling differs and the flush worker got there in a different order. It is the sibling of "cross-compiling is not evidence": the Linux runner is the one that finds races in this package, so a concurrency change is not verified until CI has seen it. The race itself was a helper whose safety depended on a lock the call site could not see — it is now `snapshotLocked`, because a name is cheaper than remembering.
   - **Both routes into the gateway go through it: the streaming endpoints and the job endpoints.** `POST /v1/upload` and `POST /v1/download` were bypassing the cache when it was first built, which made the whole feature unreachable from `odctl` — the way almost everybody uses this. The clue was in the specification and was read past: §4.4.1 adds a `phase` field distinguishing client→gateway from gateway→upstream, and a job only has two legs if it goes through the gateway. An upload now copies into the cache (`caching`), then waits for the flusher to deliver it (`uploading`), and does **not** report success until the second leg finishes — a job that succeeded when the bytes reached the cache would be telling a user their file is on OpenDrive when it is not. A file too large for the unsent allowance falls back to a direct upload, because a full cache is a reason not to cache rather than a reason to refuse an upload. The coupling is deliberately one interface four methods wide (`internal/jobs/cache.go`): the engine waits on the same notification `cache flush --wait` uses, so §10.2d's separate worker pools stay separate and there is one answer to "is it really upstream".
   - **Settled (§3.6.4, was open question #9): a write-back write is accepted while OpenDrive is unreachable.** Both routes in (`uploadTargetOrDefer`, stream and job) accept an overwrite-allowed write with an empty folder id when resolving the parent fails *temporarily*; a missing folder with OpenDrive up is still a 404, and a no-overwrite write during an outage is a 503 in words, because that promise cannot be kept blind. The flusher resolves the path with `Folders().EnsurePath` (mkdir -p, survives losing the create race, never creates on anything but not-found), and so does the job's direct-upload fallback — **an empty folder id must never reach the SDK, which reads it as the account root**; `TestADirectUploadWithNoFolderIDResolvesTheParent` fails without that guard. Unsent objects are merged into `/v1/ls` as `pending`, and a folder that exists only in the cache lists from the cache. The smoke suite kills the mock mid-run to prove it end to end.
   - **Resolve the cache before resolving upstream, in every path that takes a remote path.** This was got wrong twice in one change, in `GET /v1/download/stream` and then again in `POST /v1/download`: both looked the path up upstream first, so a file the gateway was holding but had not uploaded yet came back as a 404 — for the exact write-then-read case §3.5.3 promises against D44. A download job now needs either a file id or a remote path, not both.
   - **One gateway per cache directory, enforced by `flock` (`internal/datacache/lock.go`).** Recommending a host directory bind-mounted into the container made two writers on one journal an easy accident (`docker run` twice, or a host `opendrived` on the same folder), and a compaction from either would silently drop the other's unsent files. It is `flock`, not a pid file, because the kernel releases it when the holder dies however it dies — the moment after a crash is when the next start matters most. Consequences for tests: a test that simulates a crash by abandoning a gateway in-process must call `crashed(c)`, which does what the kernel would (close the journal, release the lock); the lock correctly refuses anything else. It is per kernel, so it does not reach across Docker Desktop's VM or a network filesystem, and the docs say so.
   - **The image runs as root (v1.3), so no folder mounted into it needs a `chown`.** Until 1.3 it ran as uid 65532, which made every bind mount a `chown` step and once left the compose file's named volume unusable. Root is compensated by distroless (no shell, no package manager), a read-only root filesystem and `no-new-privileges` in the compose file. The API key is optional everywhere since 1.3; the compose file publishes to `127.0.0.1`, and a keyless non-loopback listener is a logged warning, not a refusal. The CI docker job runs the shipped compose file with nothing prepared, signs in through the API, restarts and recreates. Bind-mount fsync on Docker Desktop is **unmeasured**, which is why the compose file offers a named volume for the cache there. Apple's `container` **was** measured (v1.2.0): a 202 survives SIGKILL of the container and is delivered after restart — and the `flock` does **not** stop a second container on the same folder, because each container is its own VM; closing that needs a lease the holder renews, not a better flock.
2.5. **A change in behaviour is not finished until the files shipped alongside it say so.** The systemd unit still had `DynamicUser=yes` and `ProtectHome=yes` after the credentials moved into the user's own folder — two directives that would have stopped the daemon reading its own `.env`, sitting in a file the deployment guide tells people to copy. The same applies to the compose file, the launchd plist, `.env.example`, the OpenAPI enum and the release notes template: anything a user follows or a machine consumes is part of the change, not an accessory to it. When behaviour moves, grep the repository for the old names — `keyring`, `ODB_STATE_KEY`, a removed flag — and fix every user-visible one in the same commit.
3. **`docs/error-taxonomy.md` and `pkg/opendrive/classify.go` are the sole authority on what an upstream failure means and whether it may be retried.** Upstream's status codes and messages routinely describe something other than what went wrong — an HTML 401 that has nothing to do with the token (D38), and a 403 whose "permission" wording is byte-identical for a transient condition and for a real denial (D39, D40). Classification takes evidence (status + body shape + Content-Type + endpoint identity, plus a rate-limited access probe where the response is not decisive); it never takes upstream's word. Consequences that are not negotiable: a non-JSON body can never yield a credential kind; nothing ambiguous or non-API-shaped may drive the auth state machine; `APIError.Temporary()`/`RetryAfter()` are the only retry authority, and no binding, pipeline or job may re-derive them. A new disguise gets a section in the taxonomy and a rule in `classify.go` — never a patch at the call site.
4. Upstream behavior: trust the live Swagger specs (`https://dev.opendrive.com/api/v1/resources/*.json`) and real sandbox responses over the PDF. Record discrepancies in `docs/discrepancies.md` — there are 53 so far, and several show the PDF is simply wrong (D12, D14, D15). Run the live suite with `scripts/integration-test.sh` (build tag `integration`) **under both test logins**: the account owner (keychain service `opendrive-bridge-test`, full write rights — D26 is the kind of bug only it catches) and an account user whose root is read-only (`ODB_SPEC_KEYCHAIN_SERVICE=opendrive-bridge-test-subuser`), which is the only login that can exercise D33, D39/D40 and the classifier's denial path. Each login skips the other's tests, so one of them alone silently loses coverage. A test that expects a refusal must remove what it made when it does not get one: two did not, and every owner run left a folder and a file in the root. Refresh the spec archive with `scripts/fetch-spec.sh`, which reads the test credentials from the OS keychain; it must run authenticated, since anonymously the explorer exposes only 21 of 220 operations.
5. Every gotcha in whitepaper §2.6 (14 items) must have at least one test case. Fuzz targets cover the two layers that read input the project does not control — upstream JSON (`pkg/opendrive/fuzz_test.go`) and caller paths (there and `internal/server/paths_fuzz_test.go`) — and they assert properties, not just the absence of panics: normalisation is idempotent, a non-JSON body can never yield a credential kind, and a path can never leave the account. A crasher found by fuzzing stays in `testdata/fuzz/` as a permanent seed; the one already there found D46. Performance is gated by `scripts/check-bench.sh`, which compares the 1 GB transfer pipelines against an MD5 of the same bytes measured in the same run, because an absolute MB/s threshold on a shared runner measures the runner.
6. Never log passwords/tokens; token redaction in logs is mandatory (§9.4). Persisting credentials is allowed **only** through the CredentialStore (`internal/keystore`: `credentials.key`, written by the daemon on sign-in) per whitepaper §9.2 — never in config files, plain files, env dumps, or process args.
7. **OpenDrive's REST API Guide is not in this repository and must not be committed.** Its copyright page forbids reproducing or transmitting it in any form, and says reproducing includes translating it into another format — so neither the PDF nor a converted copy may be added. `.gitignore` covers the path, and `docs/official-api-reference.md` says where to request it and which sources outrank it. Keep a local copy at `docs/OpenDrive_API_guide.pdf` if you have one. `docs/api-samples/` is OpenDrive's official sample code under MIT and stays, attributed. The archived Swagger specs under `testdata/spec/` are read-only, never modify. `docs/discrepancies.md` and `docs/error-taxonomy.md` are ours, are records of measured behaviour rather than restatements of the guide, and are kept current.
8. Conventional Commits; every PR includes tests; keep `main` releasable.
9. Coverage gates: `pkg/opendrive` ≥ 85%, `internal/*` ≥ 75% (§6.3).
10. **P3 summary — what upstream actually does.** Ten discrepancies came out of the transfer pipeline, and they cluster into three lessons worth carrying into P4:
   - *A 200 proves nothing.* `download/all.json` answers a file list with a valid, empty ZIP (D42); `filesettings` accepts a misspelt parameter, changes nothing and returns the full object (D43); `folder/info.json` still describes a deleted folder (D27). Always verify the effect, never the status.
   - *The error text is not the error.* An HTML 401 from a proxy has nothing to do with the token (D38); a 403 saying "permission" is byte-identical whether the cause is a real denial or a transient refusal (D39/D40). This is what `classify.go` exists for.
   - *Off-by-one and inverted fields hide in the last case.* `TotalWritten` counts the chunk, not the total (D35); a dedupe close must omit a parameter it otherwise always sends (D36); the download `offset` is honoured everywhere except the final byte (D41). Test the boundary, not the middle.
   Also settled in P3: D1 (`session_key` is ignored), D4 and D32 (no API route can consume a file password; the bridge downloads as the owner, who is never asked), D13, D44 (read-after-write is not guaranteed).
